# Передача дел: что сделано и как это работает

Документ для агента (или разработчика), который продолжает работу. Прочитайте его первым, затем `AGENTS.md`, `docs/INTEGRATION.md`
(что делать на целевой машине), `docs/GIGACODE-FACTS.md` (факты и открытые вопросы о GigaCode/MCP) и
`docs/ARCHITECTURE.md` (полный контракт: данные, REST, WS, инструменты агентов, поведение). `docs/FORK.md` говорит,
где это дерево расходится с апстримом и как забирать его исправления — на GitHub отсюда ничего не уходит.

## 1. Что это

Локальная лёгкая IDE для кодовых агентов (прежде всего GigaCode CLI) и задач, построенная по образцу Orca. Она кроссплатформенная
(Windows, Linux, macOS), Node ≥ 22, без Docker, без CDN и без телеметрии. Сервер слушает `127.0.0.1` и
защищён токеном плюс проверкой Host.

| Область | Что получает пользователь |
|---|---|
| Чаты | Каждый ход агента — это запуск GigaCode (headless `-p … --output-format stream-json`, продолжение через `--resume`) или постоянная сессия ACP. Ход показывает таймер "Working 14s", текущее действие ("Thinking", "Running: Edit…"), "Reasoned 11s", сгруппированные шаги с деталями и миниатюрами, карточку "Changed N files", разделитель "New", карточки вопросов и разрешений |
| Оркестрация | Координатор → `worker_start` → каждый исполнитель (worker) — отдельный чат (вложен в боковой панели). Агент сам запускает субагентов через `mcp__harness__agent` (те же аргументы, что у встроенного `agent`), и каждый из них — отдельный интерактивный чат. Встроенные субагенты GigaCode показываются как чаты только для чтения, построенные из потока. Ask/reply, `worker_done`, эскалации, необязательный цикл ревью силами харнеса (`reviewMode: harness`) |
| Задачи | Доска с колонками команды (To do / In progress / Testing), drag-and-drop, синхронизация из onework (назначенные мне, несколько пространств), "+ By key", значки агентов. "Take into work" запускает `/full-task <url> [notes]` в рабочем дереве (worktree) `<repo>-worktrees/<KEY>`. "Rework" запускает `/full-task <url> The task is done, but changes are needed: …`. Подзадачи в разных репозиториях через координатора. Необязательные переходы статуса в трекере при перемещении карточек |
| Git | Изменения с `+N −M`, встроенные диффы, коммит и PR с предзаполнением (`<KEY> <title>`, лимиты 100/512 байт, существующий PR не дублируется, отклонение), переключение и создание веток, переносы в `release/x.y.z` (`feature/<KEY>-rel154`, только недостающие коммиты, конфликты разбирает агент), `.superpowers/` и `.gigacode/tmp/` никогда не коммитятся; «Комментарий агенту»: «+» у строки диффа (Shift+клик — диапазон) или «Агенту» в редакторе файла отправляет «что изменить + file:lines + сами строки» в чат, который видит файл (сначала тот, что открыт в рабочем дереве, или новый; в очередь, если занят) |
| Рабочие пространства | "All projects" (папка проектов), проекты и их рабочие деревья, любая папка, дополнительные папки на чат (`--include-directories` = `/dir add`), меню рабочего дерева (открыть папку, усыпить, закрепить, удалить с проверками, массовая очистка), у каждого рабочего дерева свои вкладки |
| GigaCode | Правильный запуск (`node.exe` + `cli-entry.js` + identity из shim; в POSIX — сам скрипт), файл настроек на сессию, самовосстанавливающийся каталог моделей (`/models`, недоступные модели серые, грейды с запасным вариантом), первая авторизация (карточка со ссылкой, кнопка "Sign in to GigaCode"), установка скиллов, проверка имён моделей в файлах агентов, панель вердиктов `/full-task` |
| Надёжность | Запуски агентов переживают перезапуск харнеса (detached + повторное подключение, проверяемое по pid + времени старта), очередь доставки на диске, копии `.bak`, окно "Session recovery" после перезагрузки, терминалы перезапускаются с историей (`gigacode -c`), черновики в браузере, git никогда не зависает на запросах, пошаговый прогресс длительных операций, состояние "stalled", границы ошибок (сбой в одной панели не роняет весь экран), feature flags на случай расхождения версий клиента и сервера |
| UI | Русский язык, тёмная (как в Orca) и светлая темы, собственный набор компонентов (Select/Combobox/Popover/Menu/Dialog/...), сочетания Ctrl/⌘, настольные уведомления, `@` файлы и `/` команды во вводе, выбор модели и ветки, страница Settings с приоритетом GigaCode и значениями "Auto: …" |
| Новый пользователь и путь к влитому PR | мастер первого запуска вместо «Главной», пока не пройден или не пропущен (путь к агенту; где проекты — папка со всеми проектами или один проект; «Есть ли у вас своя команда для задач?» — нет: задача текстом, есть: своя команда; необязательно — навык для помощников), снова открывается из «Настроек» → «Мастер первого запуска» (`web/src/views/SetupView.tsx`); «Передать агенту» работает и без папки проектов; руководство пользователя — `docs/GUIDE.md`; полоса «Коммит → Push → PR → Влит» на панели изменений с «Дальше: …» и её кнопкой там, где рядом это ничего не делает («Создать PR», «Настроить», «Убрать дерево…» после слияния; `web/src/lib/flow.ts`, покрыто тестами); «+» в поле ввода прикрепляет файлы через системный диалог (копии в папке чата, сразу несколько), Ctrl+V — скриншот; очередь над полем ввода с правкой/отменой/«Отправить сейчас»; разделы боковой панели «Ждут вас» и «В работе»; «Комментарий агенту» на строках диффа |

## 2. Стек и структура

- `server/`: Node.js ESM без этапа сборки. `node:http` + `ws` + `@lydell/node-pty`. Хранилище — JSON в `data/` (атомарно + `.bak`).
  Модули: `index.js` (маршруты, безопасность, `FEATURES`, задания), `config.js`, `store.js`, `bus.js`, `launchers.js` (**вся специфика
  CLI**), `runner.js` (headless-ход: запуск detached → файлы → tail, таймауты, авторизация, отказы, остановка, повторное подключение),
  `acp.js` (транспорт ACP), `sessions.js` (сессии, очередь, терминалы, виртуальные сессии субагентов, состояния), `orchestration.js`
  (инструменты агентов, преамбулы, worker_run, цикл ревью, переносы, доработка, восстановление), `tasks.js`, `git.js`, `fs.js`, `registry.js`,
  `models.js` (каталог моделей), `mcp-client.js`, `integrations/tasks.js` (onework, markdown), `integrations/pr.js` (sourcecontrol).
- `web/`: React 19 + Vite + TS, собирается в `web/dist`. `views/` (Board, Agents, PRs, Inbox, Settings, Chat, Terminal, File,
  Diff, WorktreeHome), `components/` (Sidebar, WorkspacePanel: Files/Changes/Verdicts, board/*, chat/*, pickers/*, ui/*),
  `store.ts`, `ws.ts`, `api.ts`, `types.ts`.
- `mcp/harness-mcp.js`: MCP-сервер с инструментами оркестрации (и CLI); внедряется в каждую сессию.
- `skills/harness-orchestration/SKILL.md`: протокол для агентов; устанавливается в GigaCode как скилл.
- `commands/full-task-harness.md`: необязательная обёртка (в авто-режиме не нужна).
- `scripts/`: `mock-agent.js` (поддельный headless GigaCode; директивы ниже), `mock-acp-agent.js`, `mock-mcp.js` (поддельные
  onework/sourcecontrol, с режимом `--fixtures`), `mcp-call.js` (ручные вызовы MCP), `desktop.js` + `desktop-app.js` (окно
  приложения вместо вкладки браузера).
- `test/`: ~30 файлов `node:test`, настоящий git во временных папках с кириллицей и пробелами, `test/fixtures/` (stream, onework,
  sourcecontrol, sdd; фикстуры GigaCode реконструированы, см. `test/fixtures/README.md`).

## 3. Ключевые сценарии (подробно в `docs/ARCHITECTURE.md`)

- **Ход чата (headless).** deliver → очередь (на диске) → лаунчер (resolve, файл настроек, argv, env: identity,
  `GIGACODE_SYSTEM_SETTINGS_PATH`, `MCP_SECRET_*`, `HARNESS_*`) → detached-запуск с stdout/stderr в файлы → tail →
  нормализация (поток в стиле Qwen/Claude; события субагентов с `parent_tool_use_id` уходят в виртуальные чаты) → Messages → WS.
  `phase: starting` до первого события (холодный старт 30–60 с), `auth`, когда появляется ссылка для входа, `stalled`, когда нет вывода.
- **Взять в работу.** Если исполнитель уже запущен, возвращается его сессия (`jumped`). Иначе репозиторий
  определяется (явный, предложенный или единственный), проверяются зависимости, создаются рабочее дерево `<repo>-worktrees/<KEY>` и
  ветка `feature/<KEY>` из `targets[0]`, затем запускается исполнитель с `/full-task <url> <notes>` + короткой
  преамбулой (рабочее дерево, без коммитов, `worker_done`, субагенты через харнес). Родительская задача с подзадачами получает
  координатора в папке проектов.
- **Субагенты.** Авто-режим: блок контекста направляет модель на `mcp__harness__agent` → `worker_run` (профиль из
  `~/.gigacode/agents/<name>.md`) → временный дочерний чат → результат возвращается оркестратору как результат инструмента
  (long-poll + прогресс, переживает перезапуск харнеса). Если модель использует встроенный `agent`, из потока
  строится виртуальный чат только для чтения.
- **Вопросы/разрешения.** `ask` и инструмент вопросов GigaCode превращаются в карточку с вариантами. В GigaCode нет yolo, поэтому
  три слоя не дают ему спрашивать: "Full access" = auto-edit + список разрешённых команд по умолчанию (быстро); настоящий `auto` +
  `tools.sandbox: workspace` включается по желанию в Settings, потому что песочница замедляла запуски на реальной машине
  (самовосстановление: если песочница не стартует, используется auto-edit плюс список разрешённых команд, и пользователь получает уведомление); список разрешённых
  рутинных команд по умолчанию (`--allowed-tools run_shell_command(git)` …) на каждом ходе auto-edit/default; оставшиеся отказы превращаются в
  карточку "the CLI denied" с "Allow and retry" (разрешение на один ход, сессию или проект через `--allowed-tools`).
  В режиме ACP агент действительно ждёт ответа на `request_permission`. Как именно прошёл ход, указано в `runInfo`
  сообщения пользователя.
- **Конец хода.** Для пользователя ход заканчивается на событии `result`; зависший процесс CLI убивается после
  `exitGraceMs`. Промпты длиннее ~30K символов передаются через файл (ограничение длины командной строки в Windows).
- **Доработка.** В ту же сессию исполнителя (`--resume`, контекст сохраняется) или в новую в том же рабочем дереве; задача возвращается в "In progress".
- **Переносы в релиз, коммит/PR, трекер:** см. `README` и `docs/ARCHITECTURE.md`, разделы "Branches", "Board ↔ tracker".
- **Перезапуски.** Харнес: агенты продолжают работать и подключаются заново. Перезагрузка/сбой: сессии помечаются `interrupted`, а
  окно "Session recovery" предлагает их продолжить (или `recovery.autoResume`).

### Задача без однозначного репозитория: старт в папке проектов

«Взять в работу» использует явный репозиторий (выбранный в карточке) или предположение с ВЫСОКОЙ уверенностью (имя репозитория в
поле компонента/сервиса/репозитория задачи или в тексте); иначе агент стартует в папке проектов с промптом
задачи (например `/full-task <url>`) и пометкой выбрать репозитории из SDD (или спросить) и создать рабочие деревья по
собственным правилам (`..\<repo>-worktrees\<KEY>`, `feature/<KEY>`). Харнес привязывает к задаче каждое рабочее дерево, чья ветка содержит ключ
задачи (task.worktrees, ветка, репозиторий), и пишет в журнал «Агент создал рабочее дерево …»; Changes / коммит / PR
затем работают для каждого рабочего дерева отдельно.

### Как видеть, что делают агенты (UI)

- Боковая панель: "Needs attention" вверху (разрешение, вопрос, вход, нет вывода); проекты → рабочие деревья (одна строка, сводка
  справа) → агенты (состояние, текущее действие, модель, время); субагенты в том же рабочем дереве с `↳`, архивируются после
  завершения; дочерние в других рабочих деревьях показываются под своим рабочим деревом; терминалы как `⌨N`; служебные сессии в
  "Service". "Workspace settings": группировка, сортировка, фильтры.
- Доска: карточка показывает живое состояние своего агента, ± изменения и, после завершения агента, "Diff · Commit · PR · Rework".
- "Waiting for me" (Inbox): одна запись на сессию со встроенными действиями; счётчики ожидающих в заголовке вкладки.
- Чат: ходы в стиле Orca (таймер, текущее действие, "Reasoned", группы шагов, "Changed N files", "New"), поле ввода
  прокручивает вниз при отправке.

### Окно вместо браузера (`npm run desktop`)

Окно — тонкая оболочка Electron, харнес и агенты остаются под обычным Node (`node:sqlite`, `@lydell/node-pty` в Electron 24
отсутствуют). Два файла:

- `scripts/desktop.js` — точка входа `npm run desktop` (= `node scripts/desktop.js --ui`). Из терминала запускает Electron с
  собственным файлом и флагом `--harness-desktop`; внутри Electron показывает окно (`serve` из `desktop-app.js`); без `--ui` —
  просто сервер под Node.
- `scripts/desktop-app.js` — выбор порта (`pickPort`: от порта конфига вверх, проба `listen`), каталог данных
  (`desktopDataDir`: занят живым харнесом → `data/<slug>-<порт>`), запуск сервера (`startHarness`: ожидание `/api/health` со своим
  pid, до 20 с), остановка по `SIGINT` (`stopHarness`), окно (`showWindow`: 1440×900, без меню, заголовок фиксирован
  `page-title-updated` → `preventDefault`, внешние ссылки — в системный браузер).

Ярлык `start-harness.cmd` (Windows) и `start-harness.sh` (Linux, macOS) запускают это окно (при необходимости дотягивают
`npm install` / `npm run build`). Без терминала оба пишут журнал (`%TEMP%` / `$TMPDIR` → `sber-harness-desktop.log`) и
при сбое до окна показывают его хвост (окно сообщения в Windows и macOS, `notify-send` в Linux). `start-harness.sh` при
пустом `PATH` (Finder, пункт меню) ищет Node ≥ 22 в `PATH` login-оболочки, Homebrew, Volta, asdf, fnm и nvm. Ярлыки делает
`npm run shortcut` (`scripts/shortcut.js`): `.lnk` (Windows), `.desktop` с `Exec=/bin/sh "…"` (Linux), пакет
`~/Applications/sber-harness.app` с `LSUIElement` и иконкой из `sips` (macOS). В Linux без рабочих user namespaces и без
setuid-`chrome-sandbox` окно стартует с `--no-sandbox` (`sandboxSwitches` в `scripts/desktop.js`), иначе Chromium падает
до окна. Иконки из `build/` поставляются в репозитории; окно рисует их заново только при отсутствии (сверка по mtime после
клона ненадёжна и пачкала рабочее дерево), а `icons.mjs` внутри Electron запускается с `ELECTRON_RUN_AS_NODE` — без этого
окно навсегда зависало на сборке `.ico`. Прежняя версия `start-harness.cmd` открывала вкладку браузера с `timeout /t 2` — на холодном
старте получался белый экран, эта причина убрана совсем.

Кроссплатформенность: бинарник Electron берётся из пакета (`require('electron')` — путь к `dist/electron.exe` на Windows,
`dist/electron` на Linux и macOS), сервер запускается тем `node`, что выбран в `nodeCommand` (Electron-овый бинарник в этой роли
не используется ни на одной ОС), окно одинаково закрывается по `window-all-closed`/`activate`. `process.kill(pid, 'SIGINT')` в
Windows завершает процесс сразу (сигналов там нет) — сервер это трактует как прерванный ход.

Порядок событий, важный при доработках: `app.whenReady()` → `openUrl` (присоединение или свой сервер) → окно. Ранний
`app.quit()` и «окно мигнуло и закрылось» — это ошибка в этой цепочке: `serve` не должен возвращаться до создания окна, а
`harness` должен быть присвоен до `before-quit`.

## 5. Что делать на целевой машине

Следуйте `docs/INTEGRATION.md`; готовый промпт лежит в `docs/SETUP-PROMPT.md`. Кратко: ответьте на открытые вопросы в
`docs/GIGACODE-FACTS.md` (слияние mcpServers, хуки, схема встроенного `agent` и `parent_tool_use_id` в потоке, таймауты
MCP, инструмент вопросов, текст отказа, `--acp`, `/models`, длинные промпты, авторизация), замените фикстуры на
реальные образцы, заполните локальный конфиг, установите скилл харнеса в GigaCode (с согласия пользователя) и пройдите
чек-лист «Готово, когда».

## 6. Известные пробелы и идеи

- Режим ACP для GigaCode, хук, принудительно направляющий субагентов через харнес, и точные форматы вопросов/отказов требуют подтверждения.
- Нет статуса CI (sourcecontrol его не предоставляет); циклы "наблюдать и предлагать" для PR/CI не реализованы.
- Встроенные субагенты GigaCode нельзя отключить; харнес отводит от них модель и показывает их.
- В режиме ACP у сессии нет `pid`, поэтому "stalled" там не применяется.
- В Windows отложенный запасной вызов `process.kill(shellPid)` из node-pty при закрытии терминала отключён (он мог убить другой
  процесс, повторно занявший этот pid) патчем приватного поля (`killPty` в `server/sessions.js`). **Перепроверьте это при
  обновлении `@lydell/node-pty`.** Любое убийство процесса харнесом проходит через одну функцию, которая проверяет, что процесс
  ещё жив, и записывает причину (`killReason`).
- `test/adopt.test.js` (два теста об усыновлении CLI-чатов) падал на Linux и до подготовки к релизу: строка с папкой над
  сообщением GigaCode распознавалась только в виде Windows-пути. `FOLDER_LINE` (`server/history.js`) теперь понимает и
  существующую POSIX-папку; полностью ли это закрывает оба теста на Linux — не перепроверено.
- macOS: запуск, `.app`-ярлык (`npm run shortcut`), Dock и ⌘Q собраны по документации Electron, но на Mac не проверялись.

## 6а. Подготовка к релизу (2026-11-24): что поменялось

- Старт агентов: не больше `agents.<id>.maxStarting` (4) одновременных холодных стартов — предел на запуск, не на число
  работающих; ожидание живого процесса дольше лимита, пока растёт его stderr; временный сбой старта повторяется сам
  (20 с / 1 мин / 3 мин), сообщения ждут в очереди; зависший хук GigaCode — сообщение в чате и один повтор, хуки не
  отключаются без `agents.<id>.userHooks: false`. Подробности — `docs/ARCHITECTURE.md`, «Оживление оборвавшегося хода».
- «Переподключить MCP» (`POST /api/sessions/:id/restart { keepContext: true }`): новый процесс на той же сессии CLI.
- Чаты CLI, которые ведёт терминал, — только для чтения на 3 мин после записи CLI («Перехватить» — `force`).
- Ревью с пропавшим ревьюером — `review_stopped` («ревью прервано», `POST /api/tasks/:id/review` повторяет).
- Дубли PR: репозитории сравниваются без учёта регистра и спрашиваются один раз, открытый PR проверяется и на пути через
  агента, параллельные создания одной ветки сливаются в один вызов.
- Преамбула чата верхнего уровня (`DELEGATION`): вести задачу до конца, раздавать работу субагентам, собирать их отчёты.
- UI: «Обзор» чата (задача, дерево субагентов с отчётами, где работали, изменения, хронология) и строка исходной задачи;
  поиск Ctrl+F в чате; вложения как цельные токены; индикация отправки; стабильный порядок проектов; упрощённые фильтры и
  настройки (с поиском и навигацией); контекстные меню; карточка изменённых файлов с действиями; пояснения состояний на
  доске; список PR с вкладками статусов и фильтрами.
- Запуск: исправлен путь лаунчера в `scripts/start-hidden.cmd`, зависание окна на свежем клоне, ярлыки для Linux и macOS.

Вторая итерация (2026-11-25):
- MCP для субагентов: `orchestration.subagentMcpExclude` (Настройки → Агенты), `agent({ mcp: [...] })` при запуске и
  `mcp_enable({ server })` по ходу работы (перезапуск на той же сессии CLI).
- Мусор: архив удаляется через `sessions.purgeArchivedDays` (30), папка запуска хранит 10 последних ходов, логи
  обрезаются, папки `runs/` удалённых сессий удаляются.
- Старт: общий предел неудачных стартов подряд (4) для всех видов повторов, ожидание не дольше 2× тайм-аута,
  `session.startNote` — что пишет стартующий агент.
- Восстановление: одна строка на ведущего агента; прерванных субагентов он продолжает или останавливает сам.
- Ревью сервера: 5 исправленных ошибок (двойной ход после хука, «нет отчёта» во время повтора, лишний ход при
  «Переподключить MCP», долгий «Стоп» при ACP-старте, вечный тёплый ACP-процесс).
- UI: профилирование под нагрузкой (165 сессий) — стриминг в фоне в 3–4 раза дешевле; проход дизайна всех экранов
  (токены, контраст светлой темы, «Задачи», PR, чат и панель субагентов над полем ввода, настройки, «Агенты»);
  везде «агент / субагент», без «помощников»; панель «Изменения» для папки без git.

## 7. Разработка и отладка

```bash
npm test                     # all tests
npm run dev                  # server + Vite HMR (http://127.0.0.1:4777)
npm run desktop              # the UI in its own window (Electron); `-- --demo`, `-- --port 4790` work too
npm run demo                 # offline demo: mock agent, onework/sourcecontrol from fixtures, test repositories (port 4778)
node server/index.js --print-config   # resolved paths, launcher, models, secrets (names only)
node scripts/mcp-call.js <server> --list | <tool> '<json>'
```
Директивы агента mock в сообщении: `#spawn <spec>`, `#done <summary>`, `#fail`, `#ask <q> | <opt> | …`,
`#question`, `#deny <tool>`, `#subdeny`, `#run <profile> <spec>`, `#runwt`, `#auth`, `#crash`, `#silent`, `#slow`,
`#linger`, `#sandboxfail`, `#raw`, `/models` (актуальный список — в шапке `scripts/mock-agent.js`).
Правила: `AGENTS.md`. Контракт: `docs/ARCHITECTURE.md` (держите в синхроне). Необязательные возможности сервера объявляются в
`/api/state.features`; UI вызывает только то, что там перечислено.
